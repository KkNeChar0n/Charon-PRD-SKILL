Vibe Coding 协作 SOP

一、总览

1.1 目的

在公司 Vibe Coding（AI 辅助研发）模式已基本成熟的前提下，固化"需求 → 研发 → 测试 → 验收"四阶段协作流程，明确每一步的负责人、产出物、完成判定以及 AI 介入方式，让 AI 工具（Claude Code + Skill）成为流程的一部分而不是临时辅助。

1.2 适用范围

  • 所有走云效（阿里云效）管理的需求与迭代
  • PRD 在飞书云文档承载
  • 代码托管在公司 Git 仓库，使用 Claude Code 进行 AI 辅助编码

1.3 角色与 RACI

阶段产品研发测试研发 Leader
需求R / ACCI
研发CRIA
测试CCR / AI
验收R / ACCI

R = Responsible 执行人；A = Accountable 最终负责；C = Consulted 咨询；I = Informed 知会。

1.4 阶段流程一览

阶段主负责关键产出进入下一阶段的条件
1. 需求产品云效迭代/需求、飞书 PRD、评审纪要PRD 通过三方评审、需求状态置为"待研发"
2. 研发研发研发任务、设计文档、代码、PR、提测单代码合并主干、提测单提交、研发任务置为"已提测"
3. 测试测试测试任务、用例集、测试报告P0/P1 缺陷清零、测试任务置为"测试通过"
4. 验收产品验收清单、灰度报告、回归报告线上回归通过、需求/迭代关闭

二、需求阶段（产品负责）

2.1 云效 — 创建迭代

  • 触发条件：产品规划下个版本时
  • 操作步骤：
    1. 在 Claude Code 中执行 /aliyuncs:create-iteration
    2. 命名规则自动遵循 【项目名称 V1.X.0】，版本号自增
    3. 设置迭代起止时间、关联飞书父节点 URL（用于后续 PRD 自动挂载）
    4. 启动迭代需在云效界面手动操作
  • 产出：云效迭代实体、.aliyuncs.json 本地登记
  • Skill：aliyuncs:create-iteration（已有）
  • 完成判定：迭代在云效可见，飞书父节点已绑定

2.2 云效 — 创建需求

  • 触发条件：迭代建好后，逐条录入需求
  • 操作步骤：
    1. 执行 /aliyuncs:create-requirement，按对话补全需求标题、描述、优先级、负责人
    2. Skill 自动在飞书父节点下创建空 docx 节点，并把 feishu_url 回写到 .aliyuncs.json
    3. 需求自动关联到当前迭代
  • 产出：云效需求 + 飞书空 PRD 节点
  • Skill：aliyuncs:create-requirement（已有）
  • 完成判定：需求在云效迭代下可见，.aliyuncs.json 含 feishu_url

2.3 需求调研

  • 负责人：产品
  • 动作：
    • 用户访谈 / 业务方需求收集
    • 竞品分析（同类产品功能对比）
    • 历史数据 / 客服反馈梳理
    • 形成调研纪要附在飞书 PRD 节点开头（或单独子页）
  • AI 介入：直接在 Claude Code 对话中让 AI 帮忙做信息聚合、对比表整理（无需专用 skill）
  • 完成判定：核心问题、目标用户、价值假设、核心场景四项明确

2.4 PRD 撰写

  • 负责人：产品
  • 操作步骤：
    1. 执行 /prd-feishu <需求标题>
    2. Skill 自动匹配 .aliyuncs.json 中的需求，定位飞书节点
    3. 按统一结构生成 PRD：需求目标 / 需求简述（架构图+功能清单）/ 需求详述（状态机+原型图+逻辑补充）
    4. 原型图渲染为 PNG 上传飞书
    5. 自动向上回链：父节点目录追加 PRD 链接 + 需求目标摘要
  • 产出：飞书云文档（可协同编辑），URL 同步到云效需求描述顶部
  • Skill：prd + prd-feishu（已有）
  • 写作偏好（强约束）：
    • 不写"数据关系"章节（不列表名/字段映射）
    • 产品视角，不写技术实现细节
    • 严格按需求范围写，不补需求外的功能/入口
    • 没有真实状态流转就整段省略状态机
    • 评级/计算/分级要把规则讲具体
  • 完成判定：PRD 章节齐全，原型图覆盖所有新增/修改的页面，需求目标可在 30 秒内向新人讲清

2.5 需求评审

  • 参与方：产品（主讲）、研发、测试
  • 动作：
    1. 产品提前 1 个工作日把飞书 PRD 链接发到评审群
    2. 评审会上逐节走读，研发关注实现可行性，测试关注可测性
    3. 会议纪要直接在飞书 PRD 末尾追加"评审记录"小节，列出：参会人、变更点、待澄清项、确认时间
  • AI 介入：会前由 AI 对 PRD 做一致性自检（功能清单 vs 详述是否一一对应、原型图字段是否全在表格列出）
  • 完成判定：无 P0 待澄清项，研发/测试在飞书 PRD 末尾"评审通过"勾选

2.6 阶段 DoD（Definition of Done）

  • 云效需求状态：待研发
  • 飞书 PRD：评审通过
  • 云效需求描述顶部含飞书 URL

三、研发阶段（研发负责）

3.1 云效 — 创建研发任务

  • 负责人：研发 Leader
  • 操作步骤：
    1. 执行 /aliyuncs:create-task，针对每个需求拆分研发任务
    2. Skill 自动在每个任务下创建 前端 / 后端 / 测试三个子任务
    3. 任务标题统一格式：[需求标识] 任务名
  • Skill：aliyuncs:create-task（已有）

3.2 任务分派

  • 负责人：研发 Leader
  • 动作：在云效界面把子任务指派到具体执行人，设定预计工时
  • 原则：单子任务粒度 ≤ 2 个工作日；超过则继续拆

3.3 设计文档撰写

  • 负责人：研发（按子任务）
  • 动作：
    • 简单任务：在云效任务描述里写技术思路即可
    • 跨模块 / 涉及表结构 / 涉及对外接口的任务：必须出独立设计文档，挂在飞书 PRD 子节点下
    • 设计文档内容：接口定义、数据库变更、关键时序、风险点
  • AI 介入：在 Claude Code 对话中让 AI 基于 PRD + 现有代码生成设计草稿，研发审校
  • 完成判定：研发 Leader 在设计文档下"已确认"

3.4 代码编写（Vibe Coding 主战场）

  • 负责人：研发
  • 动作：
    1. 从主干拉特性分支 feature/<云效任务号>-<短描述>
    2. 在 Claude Code 中按设计文档驱动 AI 编码：先描述目标 → 让 AI 给方案 → 确认后实施 → 边写边跑
    3. 遵循项目既有代码风格（让 AI 先读相关模块再动手）
    4. 每个有意义的进展立即 commit；commit message 含云效任务号
  • 红线：
    • 不允许 AI 直接 push 到主干
    • 不允许 AI 跳过测试 / pre-commit hook
    • 涉及密钥、生产数据库、删除/重置操作必须人工二次确认
  • 完成判定：本地自测通过，PR 已发起

3.5 联调

  • 负责人：前端 + 后端
  • 动作：
    • 后端先在测试环境部署接口
    • 前端按接口契约联调，问题在群里 @后端 即时反馈
    • 所有接口契约变更必须同步更新设计文档
  • 完成判定：所有核心链路在测试环境跑通一遍

3.6 代码 Review

  • 负责人：研发 Leader 或同组同事 + AI 辅助
  • 操作步骤：
    1. PR 发起后，PR 描述里写清：解决什么问题、关键改动、自测情况
    2. 作者先在本地执行 Claude Code 内置 /review 做一遍 AI review，修复明显问题
    3. 再请人 review；人工 review 至少 1 人 approve 才能合并
    4. 合并策略：Squash and merge，合并后自动删特性分支
  • Skill：内置 /review（已有）
  • 完成判定：人工 approve + CI 全绿 + 合并主干

3.7 提测

  • 负责人：研发
  • 动作：
    1. 把对应云效研发任务置为"已提测"
    2. 在提测群发送提测单，内容包括：需求标识 / PR 链接 / 测试环境地址 / 影响范围 / 回归建议 / 已知风险
    3. 提测前必须保证测试环境已部署最新构建
  • AI 介入：让 AI 基于本次 PR diff 生成"影响范围 + 回归建议"草稿，研发补充后发出
  • 完成判定：测试在提测群回复"已接收"

3.8 阶段 DoD

  • 所有研发子任务在云效置为"已提测"
  • 代码已合并主干，特性分支已删
  • 提测单已发，测试已接收

四、测试阶段（测试负责）

4.1 云效 — 创建测试任务

  • 动作：测试在需求下创建测试任务（或复用研发任务下的测试子任务）
  • Skill：复用 aliyuncs:create-task 的测试子任务，无需额外操作

4.2 测试用例撰写

  • 负责人：测试
  • 动作：
    • 基于飞书 PRD 编写用例，覆盖：功能正向、异常分支、边界值、权限、兼容性
    • 用例存放位置：飞书 PRD 同级或子节点的"测试用例"文档（多维表格或脑图）
  • AI 介入：在 Claude Code 中把 PRD 链接交给 AI，让其生成用例草稿（测试人工补充异常场景）
  • 完成判定：用例覆盖 PRD 功能清单中所有"新增/修改"条目

4.3 测试用例评审

  • 参与方：测试（主讲）、产品、研发
  • 动作：
    • 评审会走读用例，产品确认业务场景无遗漏，研发指出实现细节带来的额外测试点
    • 评审纪要追加在用例文档末尾
  • 完成判定：用例集"已评审通过"标记

4.4 正式测试

  • 负责人：测试
  • 动作：
    1. 按用例集在测试环境执行，记录通过 / 阻塞 / 失败
    2. 发现缺陷直接在云效需求下建"缺陷"工作项，关联研发任务
    3. 缺陷分级：P0 阻塞主流程 / P1 核心功能异常 / P2 体验问题 / P3 文案与小问题
    4. 回归测试通过后出测试报告（飞书文档），包含：执行用例数 / 通过率 / 缺陷分布 / 风险提示
  • AI 介入：对于纯前端 UI 用例，可使用 document-skills:webapp-testing 让 AI 跑自动化用例并截图存证
  • 完成判定：P0 / P1 缺陷清零；P2 / P3 有明确处理结论（修复或挂起）

4.5 阶段 DoD

  • 测试报告已发布在飞书
  • 测试任务在云效置为"测试通过"
  • 未修复的 P2 / P3 已与产品达成共识

五、验收阶段（产品负责）

5.1 测试环境验收

  • 负责人：产品
  • 动作：
    1. 测试通过后，产品在测试环境按验收清单走查
    2. 验收点不限于"功能能跑"，更看：是否符合 PRD 预期体验、文案/视觉/交互细节是否到位、异常提示是否友好
    3. 问题在云效建"体验缺陷"或直接在飞书 PRD 末尾追加"验收反馈"
  • Skill：uat-checklist — 从飞书 PRD 自动生成验收 checklist 到飞书多维表格（Bitable）
    • 调用方式：/uat-checklist <需求标识或 PRD 飞书 URL>；如传父节点 URL 可批量处理其下所有子 PRD
    • 解析 PRD 的"功能清单 + 需求详述"章节，把每个模块/字段/规则拆成验收子项
    • 输出：在 PRD wiki 节点下创建子节点（标题="验收清单"），Bitable 共 8 列：模块 / 验收项 / 子项 / 期望表现 / 测试环境（复选框）/ 灰度环境（复选框）/ 线上环境（复选框）/ 备注
    • 同一份验收清单跨三个环境复用：测试环境验收勾左列，灰度环境验收勾中列，线上回归勾右列
    • PRD 末尾会自动追加验收清单链接，便于产品快速跳转
  • 完成判定：验收清单全部勾选通过，或未通过项已明确处理路径

5.2 灰度环境验收

  • 负责人：产品 + 研发值班
  • 动作：
    1. 研发按灰度策略发布（按用户量 / 按租户 / 按地区）
    2. 产品在灰度期内（一般 24~72 小时）观察核心指标：错误率、关键转化、用户反馈
    3. 每日同步灰度状态到群
    4. 异常立即决策：止血回滚 / 修复后继续 / 灰度比例回退
  • 完成判定：灰度期内核心指标无明显劣化，无 P0 / P1 线上缺陷

5.3 线上环境回归

  • 负责人：产品发起，测试执行
  • 动作：
    1. 全量发布后，测试按"线上回归用例集"跑一遍核心链路
    2. 产品同步在生产环境按验收清单复核
    3. 出线上回归报告
  • 完成判定：线上回归全部通过；如发现问题，按"线上缺陷"流程紧急处理

5.4 云效 — 关闭需求

  • 负责人：产品
  • 操作步骤：执行 /aliyuncs:update，批量把当前迭代下"已上线且回归通过"的需求置为"已关闭"
  • Skill：aliyuncs:update（已有）

5.5 云效 — 关闭迭代

  • 动作：所有需求关闭后，在云效界面把迭代状态置为"已完成"
  • 迭代回顾：组织一次 30 分钟回顾会，三方对照本 SOP 检查：哪一步卡了？AI 在哪些环节真正提速？哪些 Skill 体验需要改进？
  • 完成判定：迭代关闭，回顾纪要发出

5.6 阶段 DoD

  • 线上回归报告归档
  • 所有需求云效状态 = 已关闭
  • 迭代云效状态 = 已完成
  • 迭代回顾已开

七、附则

7.1 AI 使用红线（全阶段通用）

  • 不允许 AI 直接 push 主干分支
  • 不允许 AI 直接执行生产环境数据库 / 删除 / 重置类操作
  • 不允许 AI 跳过测试、CI、pre-commit hook
  • 涉及密钥 / 密码 / 客户敏感数据时必须人工确认
  • AI 产出的代码、PRD、用例、报告必须有人类负责人 review 后才能流转下一阶段

7.2 例外流程

  • 线上 P0 紧急修复：跳过完整 SOP，走单独"紧急修复"流程（PR + 至少 1 人 review + 立即灰度），事后补云效记录
  • 小于 0.5 人日的小改动：可省略设计文档、用例评审，但 PR / 测试 / 验收不能省

7.3 SOP 演进

本 SOP 每两个迭代回顾一次，沉淀的反例 / 经验同步更新到本文档，并在群内通告变更点。
